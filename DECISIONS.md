# Part C — Architectural and Design Decisions (DECISIONS.md)

### 1. Gateway Duplicate Webhook Idempotency
When the gateway delivers duplicate `paid=true` callbacks concurrently (5 ms apart), both requests pass HMAC signature verification and enter a database transaction in [src/app/api/webhooks/gateway/route.ts:69](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L69). The first request acquires an exclusive row-level lock via `SELECT id FROM gateway_bills WHERE id = ... FOR UPDATE` ([lines 72–74](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L72-L74)), while the second blocks. The first sees `status === 'pending'`, updates it to `'paid'` ([line 80](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L80)), creates and allocates the single payment ([lines 82–94](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L82-L94)), and commits. The second request unblocks, re-reads the fresh record ([line 77](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L77)), encounters `if (fresh.status === 'paid') return;` ([line 78](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L78)), and safely exits returning HTTP 200 without side effects. As a backstop, `UNIQUE(gateway_bill_id)` on the `payments` table catches duplicate inserts at [line 115](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/webhooks/gateway/route.ts#L115).

### 2. Concurrent Payment Recording and Cap Enforcement
When two staff record RM 800 and RM 700 simultaneously against a lease with RM 1,000 remaining, both requests execute `recordPayment()` in [src/lib/payment-service.ts:85](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/payment-service.ts#L85). Every transaction immediately locks the lease row via `lockLease()` using `SELECT org_id FROM leases WHERE id = ... FOR UPDATE` ([src/lib/lease-lock.ts:51–60](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/lease-lock.ts#L51-L60)). PostgreSQL serializes the execution. The first transaction computes `remainingBalance()` ([src/lib/lease-lock.ts:72–98](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/lease-lock.ts#L72-L98)) as RM 1,000 (`invoiced - allocated - pending`), inserts the RM 800 payment as `pending_verification`, and commits. The second transaction unblocks, acquires the lock, and recomputes `remainingBalance()`. Because pending payments are subtracted ([src/lib/lease-lock.ts:91–95](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/lease-lock.ts#L91-L95)), the remaining balance is now RM 200. The check `if (input.amountSen > remaining)` at [src/lib/payment-service.ts:90](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/payment-service.ts#L90) triggers, throwing `CapExceededError` and returning HTTP 422.

### 3. Date and Instant Conversions / Timezones
All calendar dates and "today" calculations strictly use `Asia/Kuala_Lumpur` (UTC+8, no DST):
1. **Invoice Status**: [src/lib/billing.ts:109–122, 243](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/billing.ts#L109-L122) derives Malaysia's date from `now` via `malaysiaDateOf(now)` to compare calendar days against `dueDate`.
2. **Collections Report**: [src/lib/reports.ts:46](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/reports.ts#L46) truncates `received_at at time zone 'Asia/Kuala_Lumpur'` to calendar months, and [line 77](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/reports.ts#L77) checks `i.due_date < (now() at time zone 'Asia/Kuala_Lumpur')::date`.
3. **Gateway Bills & Portal**: [src/app/api/leases/[leaseId]/gateway-bills/route.ts:32](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/leases/%5BleaseId%5D/gateway-bills/route.ts#L32) and [src/lib/lease-view.ts:136](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/lease-view.ts#L136) use `malaysiaDateOf(new Date())` to collect invoices due today.
4. **Gateway Timestamps**: [src/lib/gateway.ts:68–88](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/gateway.ts#L68-L88) parses timestamps with `+0800` into exact UTC Instants.
5. **Display**: [src/lib/format.ts:4–32](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/format.ts#L4-L32) enforces `timeZone: 'Asia/Kuala_Lumpur'` on formatters.

This prevents server or client local time from prematurely flagging bills overdue or misallocating collections across month boundaries.

### 4. Non-RLS Queries and Authorization Enforcement
Prisma queries run through PostgreSQL's connection pool via `DATABASE_URL` ([src/lib/prisma.ts](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/prisma.ts)), which bypasses RLS. Authorization is strictly enforced at the application layer:
1. **Authentication**: [src/lib/auth.ts:36–74](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/auth.ts#L36-L74) validates Bearer tokens or cookies using `supabase.auth.getUser()`, never trusting unverified client sessions.
2. **Identity Resolution**: Roles and tenant/org memberships are resolved solely from the database (`memberships` and `tenants` tables at [src/lib/auth.ts:76–90](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/auth.ts#L76-L90)), ignoring editable `user_metadata`.
3. **Multi-Tenant Scoping**: All queries explicitly filter by `orgId: caller.orgId` (and `tenantId: caller.tenantId` for tenants), such as in [src/lib/lease-service.ts:36–42](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/lease-service.ts#L36-L42) and [src/lib/payment-service.ts:33–44, 76–82](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/payment-service.ts#L33-L44). Access to foreign organizations returns 404 to avoid leaking existence.
4. **Role Guards**: Mutating actions (creating leases, approving/voiding) enforce `caller.role === 'manager'` in route handlers ([src/app/api/payments/[paymentId]/approve/route.ts:16](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/app/api/payments/%5BpaymentId%5D/approve/route.ts#L16)). Direct client Supabase Data API and Storage access are separately restricted by RLS policies in migrations.

### 5. Voiding Payments with Remaining Unapplied Sen
When a payment is voided, [src/lib/payment-service.ts:269–273](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/payment-service.ts#L269-L273) deletes all allocations belonging to the voided payment (`paymentAllocation.deleteMany`) and updates its status to `voided`. The system intentionally does **not** auto-reallocate `unapplied_sen` residing on other approved online payments to fill the newly reopened invoices.

**Why:** Each payment and its allocation plan is an immutable historical financial event tied to a tenant transaction and receipt. Automatically shifting funds from existing online payments across transactions would silently modify prior payment accounting, violate double-entry audit principles, and introduce race conditions during concurrent billing mutations. Instead, unapplied funds remain credited on the payment row, increasing the lease's remaining balance for future payments to allocate explicitly.

### 6. AI Assistant Errors and Resolutions
1. **Proration Denominator in `lib/billing.ts`**: The AI originally calculated the proration denominator for truncated final periods by counting inclusively to the next anchor date instead of using the positional day span `nextAnchor - anchor` ([ailogs/AIlogs.md:886–956, 1043, 1342](file:///d:/backend%20php%20larvel/ONLINE%20TEST/ailogs/AIlogs.md#L886-L956)). This improperly prorated full periods during leap years. The error was caught during unit test validation against the brief's worked example for Aisyah's lease and corrected in [src/lib/billing.ts:196–203](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/billing.ts#L196-L203).
2. **PostgreSQL Date Series String Concatenation**: In [src/lib/reports.ts:35](file:///d:/backend%20php%20larvel/ONLINE%20TEST/src/lib/reports.ts#L35), the AI generated `generate_series(${from}-01, ${to}-01, interval '1 month')` within `Prisma.sql` ([ailogs/ali Logs2.md:2528–2550](file:///d:/backend%20php%20larvel/ONLINE%20TEST/ailogs/ali%20Logs2.md#L2528-L2550)). PostgreSQL failed with a syntax error, treating `-01` as integer subtraction. The issue was identified via runtime testing and fixed using explicit SQL string concatenation: `(${from} || '-01')::date`.
